# Préversion Vercel de Quart Service

La préversion Express utilise le commit Git, Node 24 et le fichier `vercel.json` du dépôt. Le dépôt contient le script de connexion dans `public/vendor/simplewebauthn.js` pour sa publication par Vercel. À l’installation, le build vérifie que ce fichier est identique au bundle de la version npm verrouillée et copie les quatre autres bibliothèques navigateur vers `public/vendor`. Le serveur exporte l’application Express pour Vercel. Sur Render, `npm start` continue à ouvrir le port du service.

Dans le projet Vercel de test, utiliser les variables Preview existantes de l’application. Définir aussi `QUART_PREVIEW_PROJECT_REF`, `QUART_PREVIEW_SCHEMA` et `QUART_PREVIEW_DB_ROLE` pour le jeu de données à tester. Le serveur vérifie le certificat Supabase, puis le rôle et le schéma effectivement ouverts avant son initialisation. Utiliser une adresse PostgreSQL directe ou un pooler en mode session compatible avec les options de connexion. Les tests de charge doivent distinguer le plafond de trois connexions par instance du nombre total de connexions sur Supabase.

Depuis une copie propre de la branche, lier le projet Vercel de test, puis lancer `vercel deploy --environment preview`. Les origines du portail et des notifications sont propres à cette préversion. Le domaine choisi pour une passkey doit rester stable. Vérifier `/health` dans une session Vercel autorisée après chaque déploiement.

La commande d’installation exécute aussi `node scripts/prepare-preview.mjs`. Les paramètres de connexion, l’origine du portail, celle des notifications et les secrets de préversion doivent être disponibles au build comme à l’exécution. Deux builds pour le même schéma sont sérialisés par PostgreSQL. Le marqueur de version et d’origine est enregistré après la dernière étape réussie. Le serveur HTTP vérifie ce marqueur en lecture avant de servir des requêtes. Incrémenter `schemaVersion` dans `preview-schema.js` à chaque changement de schéma ou de reprise de données. Une préparation interrompue se relance au prochain build. Le coffre RH distinct reste hors du périmètre de la préversion.

La planification Vercel `quart-periodique` appelle une fonction privée toutes les 15 minutes en préversion. Le forfait Hobby peut décaler le passage dans une fenêtre de 15 minutes. Choisir la cadence et l’hébergement définitifs avant la bascule, en tenant compte des délais actuels de 30 à 120 secondes sur Render. Dans le tableau de bord Schedules, sélectionner la préversion déployée, activer la tâche puis consulter ses exécutions. Pour une répétition limitée, utiliser une date de fin. Pour un déploiement par CLI, les commandes `vercel schedules` doivent cibler l’utilisateur de déploiement avec `--user`.

Chaque passage traite les fins d’emploi, les files de courriels des congés et disponibilités, les notifications et le calendrier familial. Les fournisseurs doivent être configurés pour un envoi réel. Les rappels du coffre RH nécessitent sa propre migration. Un verrou PostgreSQL limite le traitement à un passage actif par schéma. Le journal privé `quart_scheduled_work` conserve sept jours d’identifiants de passage et de tâches terminées. Une tâche interrompue peut reprendre les éléments encore en file avec leurs clés d’idempotence ou leurs baux existants.
